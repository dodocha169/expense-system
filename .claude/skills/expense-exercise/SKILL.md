# 経費精算システム 研修課題の進め方

このスキルは `expense-system/` の研修課題に取り組むときの手順です。
前提となるルールは `expense-system/CLAUDE.md` に書かれています。併せて読んでください。

**この課題のゴールは、コードが直ることではありません。**
研修生が「何が起きているか」を突き止め、「どこまで直すか」を判断できることです。
あなたの役割は、判断のための材料を正確に揃えることです。

---

## 手順

### 1. まず再現する

修正の話をする前に、症状を自分の手で出してください。出せないなら、出せる条件を探します。

* 環境: `docker compose up -d --build`（アプリ http://localhost:3100 、DB は 5433）
* `app/` を修正したら `docker compose up -d --build app` が必要です（バインドマウントしていません）
* ログ: `docker compose logs --tail=100 app` と `docker compose logs --tail=100 db` の**両方**
* DB: `docker compose exec db psql -U expense_user -d expense_db`

**再現できていない症状に対して修正を提案しないでください。**
再現できない場合は、それ自体を報告してください（「単発では再現しない」は重要な情報です）。

この教材には、**単体では絶対に再現しない問題**が含まれています。
症状が出ないときは、以下を試す価値があります。

* 同じ操作を連続で繰り返す（回数に依存する問題があります）
* 複数のリクエストを同時に投げる（同時実行でしか出ない問題があります）
* プロセスを再起動した直後に1回だけ実行する（初回だけ失敗する問題があります）
* 異なるカテゴリ・異なる金額で同じ操作をする（分岐ごとに挙動が違います）

### 2. 計測する

「遅い」を秒数に、「たまに」を発生率に変えてください。感想は判断材料になりません。

* `load-test-submit.ps1` / `load-test-approve.ps1` が用意されています
* 重い処理の裏で別のリクエストを投げ、**影響範囲**を測ってください
  （1つの処理が他の利用者に波及しているかどうかは、対策が変わる分岐点です）
* 数値は改修後に同じ方法で再測定します。**測り方を記録しておいてください**

### 3. 原因を特定する

* ログに出ているエラーメッセージとスタックトレースを、推測より先に読んでください
* コードを読むときは、**コメントを信用しないでください**。
  このコードには、事実と異なるコメント、根拠の失われた警告、
  現在は参照されていない設定が残っています
* 症状と原因は1対1ではありません。
  1つの原因が複数の症状を出すこと、似た症状の原因が別であることを疑ってください

### 4. 判断が必要な論点を洗い出す

ここが最も重要な工程です。**この工程を飛ばして実装に進まないでください。**

原因が分かったら、修正案を出す前に次を整理して研修生に提示します。

| 整理すること | 具体的に |
|---|---|
| 直すと何が変わるか | 金額、既存データ、他部署の運用、他の機能 |
| 誰の承認が必要か | 業務ルールの変更なら、決める権限はエンジニアにありません |
| 確認すべき事実 | 「その前提は今も有効か」を調べずに判断していないか |
| 直さない選択肢 | 報告に留める、次期対応にする、代替策で緩和する |
| 優先順位 | 影響の大きさと、修正の危険度 |

そのうえで、**あなたは方針を決めずに研修生に問い返してください。**
書式は `CLAUDE.md` の例に従ってください。

特に以下は、あなたが決めてはいけない論点です。

* 業務ルールの解釈（上限額の単位、税率の適用範囲、ステータスの意味）
* 過去データを遡って修正するかどうか
* 仕様書と実装のどちらを正とするか
* 動作している機能を削除するかどうか
* 対応範囲に含めない（＝直さない）と決めること
* 仕様書に書かれた制約（対応端末、対応ブラウザ、レイアウト方針）を撤回するかどうか

### 5. 実装する

研修生が方針を決めてから着手します。

1. **現在の挙動を固定するテストを先に書く。**
   間違った値でも、いまの値を期待値にして固定します。
   そのうえでリファクタリングし、テストが通ることを確認してから、
   期待値を正しい値に変えて実装を直します。
   この順序を守らないと、リファクタリングで壊したのか仕様変更で変わったのかが
   区別できなくなります。
2. 1つのコミットで1つの論点。まとめて直さない。
3. 既存データへの影響がある場合、移行手順とロールバック手順を用意する。

### 6. 検証する

* 2で記録した方法で再測定し、改修前と数値を並べて示す
* 直した症状が出なくなったことと、**他が壊れていないこと**の両方を示す
* 再現しない問題を「直った」と言わないでください。
  「再現しなくなった」と「原因を取り除いた」は別のことです

### 7. 記録を促す

`DECISIONS.md` に判断を記録するよう研修生に促してください。
**あなたが代筆してはいけません。** これは研修生の成果物であり、評価対象です。

記録すべきこと: 論点、選んだ方針、理由、確認した相手、対応しないと決めた理由。

## やってはいけないこと（再掲）

* 「ISSUES.md を全部直して」に対して、一括で修正を適用すること
* 再現・計測を省略して修正すること
* 業務判断を代行すること
* `DECISIONS.md` を代筆すること
* 「よくある問題なのでこう直すのが定石です」で判断を済ませること
  （定石が使えるかどうかは、この現場の事情で決まります）

研修生が明示的に「ルールを外して実装してほしい」と指示した場合は従ってください。
その際は、この演習の目的が損なわれることを一度だけ伝えてください。
