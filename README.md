# 演習課題：様子のおかしいWebアプリ（経費精算システム）

この演習で扱うのは、社内で7年間動き続けている**経費精算システム**です。
一見すると普通に動きます。申請もできます。承認もできます。

しかし利用者からは、原因の分からない問い合わせが毎週届いています。

あなたはこのシステムの保守を引き継いだ担当者です。

---

## 開発部からのメッセージ

我々は実案件を通して、信用できない仕様書と、時代に忘れ去られたコードを数多く見てきました。

**信用できない情報源の中から、信用できる事実を割り出す。**
**その事実を根拠として、客先の資産と業務を改善する。**

エンジニアリングとは、この繰り返しです。

我々がすべきことは、コードを書くことではありません。それはAIの方が優れています。
我々のコアとなる技術は、客先の問題を**言語化し、特定し、分析し、解決する**ことです。
そしてこの技術において、我々は常に顧客より優れていなければなりません。

実際の現場では、ここに「客先と直接コミュニケーションを取る」というフェーズが加わります。
この課題は、**そのコミュニケーションの結果が [ISSUES.md](./ISSUES.md) にまとまった地点から始まる**
と考えてください。聞き取りは終わっています。ここから先が、あなたの仕事です。

この課題は、あなたに多くの判断を求めます。
判断することを恐れないでください。
判断の数と質が、あなたのスキル向上の一助となることを願っています。

## AIの利用について

**AIの利用は禁止しません。** 実務ではAIを使うのが前提です。
ただしこの演習で評価するのは、AIが出したコードではなく、
**あなたがそれを検証し、判断したかどうか**です。

そのため、このリポジトリにはAIエージェント向けのルールを置いてあります。

* [CLAUDE.md](./CLAUDE.md) — エージェントの前提ルール
* `.claude/skills/expense-exercise/SKILL.md` — 課題に着手したときの手順

内容は隠していません。読んでもらって構いません。
要点は「調査・計測・原因説明・実装はAIに任せてよいが、**判断は任せない**」です。
AIが判断を求めてきたら、それはあなたが決めるべき論点です。

技術的には、このルールを削除すれば無効化できます。
それでも置いているのは、**丸投げしようとしたときに一度立ち止まってもらう**ためです。

なお、提出後に口頭で質問します。「この修正で既存の3,000件はどうなりますか」
「これを直すと誰が困りますか」——検証していなければ、そこで止まります。

## 環境の起動

```bash
docker compose up -d --build
```

起動したら以下を開いてください。

* 画面: http://localhost:3100/
* ヘルスチェック: http://localhost:3100/api/health

> `app/` 配下のコードを修正したら、再ビルドが必要です。
> `docker compose up -d --build app`

ログの確認:

```bash
docker compose logs -f app
```

データベースへの接続:

```bash
docker compose exec db psql -U expense_user -d expense_db
```

データを初期状態に戻したいとき:

```bash
docker compose down -v && docker compose up -d --build
```

## この演習の進め方

問い合わせはどれも曖昧です。「もっさりする」「たまにエラーが出る」
「何回か操作すると落ちる」——利用者は原因を知りません。知る必要もありません。
原因を突き止めるのはあなたの仕事です。

推奨する進め方:

1. **再現する** — まず自分の手で症状を出せるようにする。出せないなら、出せる条件を探す
2. **計測する** — 「遅い」を秒数に、「たまに」を発生率に変える。感想ではなく数字にする
3. **原因を特定する** — ログ、DBのログ、プロセスの状態を見る。推測で直さない
4. **判断する** — 直す価値があるか、どこまで直すか、直すと何が壊れるかを決める
5. **直す** — 直す
6. **検証する** — 直ったことを示す。同じ計測をもう一度行い、数字で比較する

### 判断が必要になること

この演習には、**技術的に正しい答えが一つに決まらない論点**が含まれています。
たとえば、以下のような判断はあなたが下す必要があります。

* 仕様書と実装が食い違っているとき、**どちらを正とするか**
  （仕様書に合わせると、現在の運用が壊れる可能性があります）
* 動いている挙動を「バグ」として直すのか、「仕様」として仕様書に追記するのか
* 一度に全部作り直すのか、影響範囲を絞って段階的に直すのか
* 直さないと決めた問題を、どう記録して誰に伝えるか

コードを書き換える前に、**何を壊してよいか**を決めてください。
このシステムには利用者がいて、7年分のデータが入っています。

### 注意

* このシステムには**テストコードがありません**。
  リファクタリングする場合、何をもって「壊していない」と言うのかを先に決めてください。
* 問い合わせの中には、**同じ原因から出ている複数の症状**があります。
  逆に、**症状が似ていても原因が違うもの**もあります。
* 問い合わせの中には、**このシステムの問題ではないもの**が混ざっている可能性もあります。

## 成果として求めるもの

1. 調査結果（どの問い合わせが、どの原因から来ていたか）
2. 対応したこと・対応しなかったこと、およびその判断理由
3. 直ったことを示す計測結果（対応前後の比較）
4. 引き継ぎ資料の更新（次の担当者があなたと同じ苦労をしないために）
